# ASKA v5 — Interoperability, standards alignment, and migration

## 1. No mandatory legacy substrate

The native ASKA target is not a POSIX/Linux/IPv4 host with labels added to one shared socket stack. It is an object/effect machine with purpose-separated endpoint and network paths, explicit authority negotiation and independently guarded outputs. A deployment may still run Linux or ordinary web services inside **declared compatibility islands**, and Wilder is the default quarantine/legacy encounter path. Compatibility does not create an exemption from physical and effect boundaries.

## 2. Standards alignment

| Area | Candidate established components | ASKA-specific obligation beyond the component |
|---|---|---|
| Claim encoding | CBOR/COSE or other reviewed canonical signed formats | type/domain separation, profile binding and rejection of critical unknowns |
| Identity | W3C Verifiable Credentials where appropriate, digital identity assurance guidance | action-specific validity and minimum necessary disclosure |
| Attestation | RATS architecture / SPDM and vendor roots | independent relying-party authorization and genuine physical separation evidence |
| Confidential channels | TLS, HPKE, authenticated encryption, hybrid post-quantum suites | exact object/effect binding and no implicit disclosure from session membership |
| Path transport | admitted circuits, installed tables, SCION-family technologies | current guarded physical port checking and distinct purpose fabrics |
| Native cell implementation | small verified kernels, capability machines, RISC-V, specialized object engines | exclusive resource ownership and complete mediation including DMA/management |
| Witness | hash chains, signed checkpoints, independent storage/replication | confidentiality, qualified notice, fail-closed/degraded behavior |

These technologies are building blocks rather than proof that the integrated design exists. The [source register](30_sources_and_evidence.md) records concrete comparisons and evidence limits.

## 3. Migration phases

**Stage A — semantics:** implement PACT evaluator and typed grants with strong unit tests; show contract non-expansion independently of a network. **Stage B — protected endpoints:** enforce cells, object ownership and effect finality on a local demonstrator. **Stage C — physical planes:** add independent interfaces, dedicated ingress resources, Steles and protected Keystone UI. **Stage D — community networking:** deploy a bounded neighborhood node and demonstrate actual link/failure dependencies, local service and guarded crossings. **Stage E — high-assurance qualification:** independently validate update/recovery roots, physical threat model, formal abstractions and human-factors behavior.

No stage may be described as full native conformance if it lacks required machine/plane properties.

## 4. Legacy import and export

A legacy device can connect through a guarded adapter classified as Wilder or another explicitly constrained endpoint. It must not speak raw root policy or arbitrary protected receive memory. A legacy exporter can transmit only a narrowly constructed output after source release, independently accepted destination and physical-path authorization. A trusted adapter may expose familiar APIs to one confined IES but not expose all ASKA objects as a host filesystem.

## 5. Interoperability behavior

Peers negotiate a common suite and profile without silent fallback. If one endpoint cannot implement the other party's physical or cryptographic assurance constraint, it reports `profile_mismatch` or `cannot_enforce_obligation`. A user or institutional officer may initiate a **new explicitly weaker contract** only if the applicable profile permits that alternative. A signed record generated under a weak deployment must not claim it came from hardware-disjoint paths.

## 6. Backward compatibility and forward evolution

Use stable semantic object IDs with versioned schemas, a signed capability/extension registry, and pinned policy/transcript hashes. New signing or post-quantum algorithms require deliberate migration, re-enrollment where necessary and verified anti-rollback. Old receipts must remain verifiable without forcing indefinite acceptance of obsolete signing keys for new grants. Contexts and credentials should be independently upgradeable so a compromised commercial issuer does not force household or civic root replacement.

## 7. Industrial deployment and open governance

An open reference implementation should publish schemas, formal models, negative vectors, wire compatibility tests, a reproducible build procedure, hardware interface requirements and an evidence register. Governance profiles may be locally selected by jurisdictions and institutions, but no jurisdiction may silently redefine the physical guarantee asserted by a device under an unchanged assurance identifier. Building trusted silicon with separate chiplets, mature-node guard blocks, alternative compute cores and diverse suppliers is an architecture option that needs measured engineering and supply-chain evidence, not a promise of automatic immunity.
