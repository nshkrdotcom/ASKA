# ASKA v6 — Passive hardware observation, event provenance and limits

**Status:** normative sensor-interface contract with experimental implementation candidates. Sensor coverage must be demonstrated against the precise silicon and storage topology; no claim of universally transparent RAM/SSD monitoring is assumed.

## 1. What passive means

A **passive observation tap** is a connection whose declared data path cannot issue, modify, acknowledge on behalf of, reorder, block or inject transactions into the observed resource. Its allowed electrical and logical influence is explicitly characterized. A read-only DMA device is not necessarily passive: it issues reads, consumes memory/interconnect bandwidth, can observe protected plaintext, and may induce timing or fault behavior. A privileged debug controller is not passive merely because its current firmware promises not to write. A software event collector called from the OS is in-band with that OS's authority.

A passive tap is out-of-band relative to a monitored workload only if the workload cannot change its firmware, sampling filters, clock/counters, exported observations, or access constraints. Taps are inputs to a separately rooted LSM or watcher, not a route for repair code into RAM. A sensor may be inline as a mandatory enforcement point, but that must be described as **guard instrumentation**, not passive monitoring.

## 2. Explicit observation taxonomy

| Mode | Candidate signals | Security claim it can test | Important limitation |
|---|---|---|---|
| Physical bus mirror / sideband trace | Address-class events, bus requests, protected tags, access denial, DMA requester ID | Access patterns *visible at the tap* and guard decisions | Caches can hide operations; snooping electrical integrity and completeness must be measured |
| Protected on-chip event export | Local fault counters, classified memory-boundary events, IES transitions, interconnect arbitration | Events generated by trusted silicon and emitted one way | The generator is in the silicon TCB; internal bugs or compromise can lie/omit |
| Storage-controller sideband | NVMe command metadata, controller rejects, flash writes, media status | Interface-visible I/O, selected integrity state and endurance | Not complete file semantics; FTL, encryption, volatile caching and wear leveling obscure contents |
| External link / packet tap | Frames and timing on an actual media segment | Observed link traffic and selected policy rejects | Encrypted payload opaque; taps miss alternate links and offline effects |
| Protected snapshot service | Explicitly granted memory region or immutable extent | Content inspection under a release/admission contract | Active read/copy operation, confidentiality exposure and performance costs |
| Analog / physical emission sensor | Power, electromagnetic, thermal or optical patterns | Limited anomaly correlation under calibrated conditions | Highly noisy, privacy-sensitive and not a proof of instruction semantics |

A sensor manifest MUST separate `physical_observed`, `protected_exported`, `actively_sampled` and `derived_inference` fields. Do not present inferred behavior as a direct measurement. Sampling claims include period, dropped-event bound, resolution, clock precision, and maximum bursts before saturation. False negatives remain possible even with correct hardware.

## 3. RAM and CPU observation boundaries

An external memory-channel probe cannot see every register operation, on-core cache hit, speculative instruction, or access fully satisfied in another private cache. Encrypted memory may expose transactions and metadata without exposing protected contents. An IOMMU record may show a denied DMA attempt but not a malicious program's intent. A complete statement about *all memory reads* requires trusted on-core instrumentation, exhaustive architectural tracing or a proof under a restricted execution model; an off-chip tap alone cannot justify it.

The high-assurance option is to combine independently enforced isolation with protected, bounded event-export signals at mandatory guard points. The protected exporter has a small finite schema and cannot receive arbitrary commands from the observer. The observer is free to be wrong about inference but cannot alter the access decision already made. Every exported source is authenticated to its physical root and current IES/allocation generation; a software-writable PID, address, label or `ies_id` is not sufficient provenance.

For snapshots, the owning guard resolves the object and generation, then binds a coherent immutable copy or exclusive transfer. The observer receives no broader rights than the approved snapshot contract; classification, output and retention restrictions follow [13](13_memory_ownership_and_lifecycle.md), [15](15_authority_and_information_flow.md) and [19](19_cross_domain_security_and_release.md). Snapshotting cannot be used as a hidden exception to Sanctum confidentiality.

## 4. SSD and persistent-media observation boundaries

A device may acknowledge a write before its effect becomes durable, reorder requests through caches, remap physical flash through a flash-translation layer or perform internal garbage collection. A storage-side observer cannot infer durable application commit solely from seeing an NVMe write command. It must correlate the storage owner's durable receipt, controller flush semantics, media generation and device trust profile. An encrypted disk may obscure content; an attacker controlling a device controller may forge its own telemetry unless an independent boundary constrains that controller.

A read-only media mirror is distinct from a recorder that clones data continuously. Cloning creates sensitive copies, a retention lifecycle, device wear and a new disclosure path. Such implementations require explicit data authority, physical guard checks, inventory, deletion and recovery contracts. An untrusted observer is never granted a universal decrypted-storage key to simplify forensic analysis.

## 5. Evidence record

Each emitted `SENSOR_EVENT` MUST bind at least the following semantic fields; wire representation remains profile-pinned:

```yaml
kind: aska.security.sensor_event
revision: 1
source: {root: tap-root-A, sensor: mem-guard-3, generation: 41}
observed_scope: {ies: opaque-ies-17, generation: 8}
observation: {type: denied_dma, class: protected_exported, count: 1}
sequence: 98301
time_basis: {clock_id: local-monotonic-2, tick: 2345687, uncertainty_ns: 600}
coverage: {sampling: full_for_named_guard_event, missed_since_previous: 0}
label: {category_ref: local-security-events}
evidence: {digest: "sha256:<illustrative value>"}
```

The illustration contains no signature or valid hash and is **not a cryptographic test vector**. A profile binds type/version, source root and key role, sequence monotonicity, observation scope, clock error bound, report confidentiality and event integrity. Mixed-clock comparisons require explicit uncertainty intervals; lack of synchronized time must not silently fabricate causal order.

## 6. Loss, saturation and bounded influence

The tap path MUST have an explicit buffer policy: bounded queue capacity, overwrite/stop semantics, drop counters, maximum interrupt rate and backpressure handling. A supposedly passive tap that blocks the workload bus when its queue fills is not passive under that definition. Dedicated security reporting bandwidth is measured under hostile workload rate and telemetry-flood conditions. Where reporting drops, the report advertises incomplete coverage instead of emitting a normal heartbeat.

An active monitoring profile MAY trade performance for stronger inspection, but must be named separately and measure memory bandwidth, I/O latency, power, device wear, coherence perturbation, privacy exposure and new attack paths. Direct access via debug/JTAG, memory test ports, BMC interfaces or unfiltered chiplet fabric must be either physically disabled or included in the enforcement threat graph. A protected test interface is not a universal exception to R21/R22.

## 7. Integrity, privacy and defensive usefulness

An authenticated observation proves attribution to a protected exporter, not the truth of a host process's log line or the correctness of an AI explanation. The receiving LSM checks identity/generation, types, loss, replay, category and budget before using the event. Sensor data can itself disclose addresses, activity, identities, medical context, membership, user behavior or cryptographic side channels; its access and retention require ordinary Accord authorization. Aggregated security metrics are not automatically public.

Evaluation uses a truth-instrumented reference rig where possible. Report precision, recall, detection latency distribution, visibility by attack class, false alarms per device-day, missed coverage, benign overhead and stress-case degradation. Do not generalize beyond the visibility actually established. [43](43_security_mesh_formal_model_and_test_vectors.md) supplies fault and substitution tests; [45](45_research_frontier_and_independent_validation.md) lists the unresolved physical techniques.
